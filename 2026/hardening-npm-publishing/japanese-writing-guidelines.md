# 日本語表現ガイドライン

この発表資料を Codex で編集するときの表現ルール。

目的は、発表者の感覚や比喩に寄せすぎず、技術資料として説明可能な言葉にそろえること。

## 基本方針

- 比喩よりも、対象、範囲、関係、条件、経路を明示する
- 「強く見せる」よりも「何を説明しているか」を優先する
- 攻撃者視点の説明は使ってよいが、煽りや戦闘的な言い方に寄せない
- 断定するときは、根拠となる仕様、事例、設定、制約に対応させる
- スライド本文は短く、発表者ノートで補足する

## 避ける表現

| 避ける表現 | 理由 | 置き換え候補 |
| --- | --- | --- |
| 刺さる | 聞き手の反応を決めつける感覚語 | 伝わりやすい / 説明しやすい / 対応関係が明確 |
| 効く | 口語的で、何に対応するかが曖昧 | 対応する / 緩和する / 制御する / 減らす |
| 主戦場 | 戦闘的な比喩が強い | 焦点 / 対象範囲 / 中心になる箇所 |
| 地図 | 比喩が前に出る | 脅威モデル / 分類 / 対応関係 |
| 権限に化ける | 口語的で曖昧 | 権限が広がる / publish 権限につながる |
| ジャンプ地点 | 比喩が強い | 権限境界 / 権限が広がる地点 / Approve stepを置く地点 |
| 何重にも止める | 強調表現で雑に見える | 複数の段階で制御する / 複数の緩和策を置く |
| 固める | 抽象的 | 制御する / 保護する / 緩和策を置く |
| 塞ぐ | 口語的で強い | 閉じる / 制限する / 緩和する / 制御する |

## 推奨する語彙

- 対応する
- 対応関係
- 対象範囲
- 脅威モデル
- 分類
- 経路
- 権限境界
- Approve stepを置く
- Approveを挟む
- 制御する
- 制限する
- 緩和する
- review を追加する
- 長期 token を使わない
- publish 経路を限定する

## SLSA の説明方針

SLSA は、この発表では「達成レベル」ではなく「脅威モデル」として扱う。

避ける:

- SLSA の地図
- SLSA に沿って守る
- SLSA を達成する話に見える説明

使う:

- SLSA の脅威モデル
- SLSA の分類
- SLSA の Artifact publication(F) に対応する話
- npm publish の対策を SLSA の分類へ対応づける

## 例

Before:

> OIDC・environment・staged はどれも (F) を多層で固める。

After:

> OIDC、Environment、staged publishing は、いずれも Artifact publication(F) に対する緩和策として位置づけられる。

Before:

> Environment は publish 権限に化けるジャンプ地点を止める。

After:

> Environment は、GitHub の権限が npm publish 権限へ広がる地点にApprove stepを置く。

Before:

> この図は聞き手に刺さる。

After:

> この図は、各対策と SLSA の脅威分類の対応関係を説明しやすい。

## Codex への指示

このディレクトリのスライド、発表者ノート、図の文言を編集するときは、このガイドラインを参照すること。

特に以下の語を追加した場合は、より具体的な表現へ置き換えられないか確認する。

- 刺さる
- 効く
- 主戦場
- 地図
- 化ける
- ジャンプ
- 固める
- 塞ぐ
