## textlint MCP デモの詳細手順

### 事前準備（前日まで）
1. **デモ環境の準備**
   - textlint v14.8.0以降がインストールされていることを確認
   - MCP対応のAIアシスタント（Claude Code推奨）のセットアップ
   - デモ用のMarkdownファイルを用意（意図的なエラーを含む）

2. **デモファイルの内容例**
```markdown
# デモ用ドキュメント

このドキュメントはtextlintのMCP統合のデモです。

JavaScript と Javascript の表記揺れがあります。
また、コールバックとcallbackの混在もあります。

これはとても長い文章で、読みにくいかもしれません。なぜなら、一つの文に複数の内容が含まれているからです。そして、それがさらに続いているからです。
```

3. **バックアッププラン**
   - デモが失敗した場合の録画ビデオを用意
   - スクリーンショットで手順を説明できるようにしておく

### 当日のデモ手順（2分以内）

**Step 1: MCP起動（15秒）**
```bash
npx textlint --mcp
```
> 「まず、textlintをMCPサーバーとして起動します」

**Step 2: AIアシスタントからの呼び出し（30秒）**
- Claude Codeでデモファイルを開く
- 「このファイルをtextlintでチェックして」と指示
- AIがMCP経由でtextlintを呼び出す様子を見せる

**Step 3: 結果の説明（45秒）**
- 検出されたエラーを説明
  - 表記揺れ
  - 文の長さ
  - その他のルール違反
- AIが改善提案を出す様子

**Step 4: 自動修正（30秒）**
- 「修正してください」と指示
- AIがtextlintの--fix機能を使って修正
- 修正後のファイルを見せる

### デモのトラブルシューティング

**問題：MCP起動に時間がかかる**
→ 事前に起動しておく

**問題：AIアシスタントが応答しない**
→ バックアップビデオに切り替え

**問題：想定外のエラー**
→ 「これは想定外のエラーですが、通常はこう動作します」と説明して次へ

### デモ後のフォローアップ
> 「このように、AIアシスタントがtextlintを直接呼び出せます。これにより、AI生成文章の品質を即座にチェック・改善できます。AI時代における品質管理の新しい形です」

## 質疑応答で予想される質問と回答

### Q1: 「14年間一度も欠かさず配信」は本当に可能なのか？
**A:**
> 「はい、可能でした。鍵は『データドリブンな公開基準』です。期間で区切らず、13記事集まったら公開するルールにしたことで、プレッシャーを排除できました。また、自動化システムで更新コストを小さくしたことも大きいです」

---

### Q2: GitHub Sponsorsで生活できるのか？
**A:**
> 「完全に生活できるわけではありませんが、年間約260万円の収入があります。これはプロジェクトの継続に必要なコスト（年間30日分の労力、約70万円）を十分にカバーできる金額です。また、Open Collectiveと組み合わせることで、持続可能な経済モデルを構築できました」

---

### Q3: AI時代にtextlintは不要になるのでは？
**A:**
> 「逆です。AI時代だからこそtextlintが必要です。AIは一貫性のない文章を生成することがあります。textlintのような品質基準を持つツールで検証することで、AI生成文章の品質を保証できます。MCP統合により、AIとtextlintが協調して動くようになりました」

---

### Q4: 100人とどうやって協働しているのか？
**A:**
> 「鍵は透明性と設計文書です。各章にOUTLINE.mdという設計文書を用意し、『なぜこの章が必要か』『何を学ぶか』を明確にしました。また、すべての議論をGitHub上で公開し、誰でも参照できるようにしました。さらに、Fibonacci報酬システムで貢献度に応じた報酬を支払うことで、持続可能な協働を実現しました」

---

### Q5: 技術的依存と心理的依存の区別をどう実践すればいいのか？
**A:**
> 「まず、自分のプロジェクトで『〜しなければならない』と感じることをリストアップしてください。そして、それぞれについて『これは技術的な必要性か、それとも自分が作り出したプレッシャーか』を問いかけてください。例えば、『毎週月曜に公開しなければ』は心理的プレッシャーです。『13記事集まったら公開する』に変えることで排除できます」

---

### Q6: Living Standardアプローチは他の分野でも使えるのか？
**A:**
> 「はい、使えます。特に技術が急速に変化する分野では有効です。鍵は『Web版で常に最新』『書籍版はスナップショット』という二層構造です。これにより、常に最新の情報を提供しつつ、安定版も用意できます」

---

### Q7: 小さなイテレーションの具体的な方法は？
**A:**
> 「JSer.infoでは『1紹介=1コミット』という小さな単位で作業します。大きな記事を一度に書くのではなく、小さく分割して、失敗した時の後戻りを小さくします。jsprimerでも、Design DocからAI Agentで初稿を生成し、段階的に改善するアプローチを取っています」

---

### Q8: GitHub Sponsorsの見返りを用意しない理由は？
**A:**
> 「見返りを用意すると、それを提供する義務が生まれます。これは心理的プレッシャーになり、燃え尽きの原因になります。代わりに、透明な資金運用と年次報告で信頼を構築しています。スポンサーは『プロジェクトの継続』という価値に対して支援してくださっています」

---

### Q9: textlintがNo core rulesを選択したデメリットは？
**A:**
> 「初心者にとっては最初のハードルが高いことです。インストールしても何も起きないので、『どうすればいいのか』を学ぶ必要があります。でも、これは意図的なトレードオフです。長期的には、ユーザーが自分に最適なルールを選択できる柔軟性の方が価値が高いと判断しました」

---

### Q10: AI Agent（Iterator Helpers章）の具体的な使い方は？
**A:**
> 「Design Docを作成後、そのOUTLINE.mdをAI Agentに渡して初稿を生成してもらいます。重要なのは、Design Docで『何を書くか』を明確にしておくことです。AIは方向性が明確な場合に最も有効です。生成された初稿は、その後人間がレビュー・改善します」
