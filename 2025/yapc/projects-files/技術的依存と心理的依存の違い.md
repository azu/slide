# 技術的依存と心理的プレッシャー - 継続の設計原則

## 結論

15年間のOSS開発を通じて発見した継続の設計原則：

- **技術的依存**：継続する理由を増やす（育てる）
- **心理的プレッシャー**：継続の理由にはならない（軽減する）

## 継続という軸での対比

### 技術的依存

**継続する理由を増やす ✓**
```
使っているから続けたくなる
  ↓
続けるほど価値が増える
  ↓
複利効果で自然に継続
```

**特徴：**
- 「続けたい」を作る設計
- 内発的な動機
- プロジェクト間の相互強化
- エコシステムの成長

**具体例：**
- jsprimerでtextlintを使う → textlintが改善される
- JSer.infoのデータセット → AI時代で価値が増す
- 100以上のtextlintルール → エコシステムの成長

### 心理的プレッシャー

**継続の理由にはならない ✗**
```
「続けなければならない」義務感
  ↓
短期的な動機にはなる
  ↓
長期化すると燃え尽きる
```

**特徴：**
- 「続けなければ」で動く状態
- 外発的な動機
- 慢性化すると継続の障害
- 短期的には機能するが持続しない

**具体例（排除した設計）：**
- JSer.info：「毎週月曜に公開」→「13記事集まったら公開」
- textlint：「全てのルールに対応」→「No core rules戦略」
- GitHub Sponsors：「スポンサーに特典提供」→「見返りなし」

## 設計原則

### 技術的依存を育てる

プロジェクト間の相互依存を意図的に設計する：
```
jsprimer → textlint → HonKit
    ↓         ↓         ↓
 使っているから続く
 続いているから使う
```

### 長期的な心理的プレッシャーを軽減する

構造的な設計で慢性的なプレッシャーを防ぐ：

- データドリブンな判断基準
- 明示的な選択の仕組み
- トイル（定常作業）の自動化
- 透明な経済モデル

## 注意点

**適度な短期的プレッシャーは有益**

- 締め切りによる集中力
- マイルストーンによる達成感
- 一時的な負荷は成長の機会

**問題は慢性化**

短期的なプレッシャーが長期化すると、継続の障害になる。設計で構造的に軽減することが重要。

## まとめ

**継続の動機を内発的にする設計**
```
【技術的依存】
継続する理由を増やす
→ 「続けたい」が生まれる
→ 複利効果

【心理的プレッシャーの軽減】
「続けなければ」に頼らない設計
→ 燃え尽きを防ぐ
→ 持続可能性
```

**効率化ではなく持続可能性を設計する**
