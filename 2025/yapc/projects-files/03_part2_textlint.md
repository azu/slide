## Slide 18: 読む技術 - 文章を「読む」とは？

### ビジュアル
- ASTの概念図
- Markdown → AST → ルール適用の流れ

### コンテンツ

```
文章を「読む」とは？

人間が読む：
意味を理解する

textlintが読む：
AST（抽象構文木）を解析する

フロー：
文章 → Markdown Parser → AST
     ↓
   ルール適用
     ↓
エラー検出・自動修正

構文を理解した品質検証

https://textlint.github.io/docs/txtnode.html
```

### スピーカーノート
- 「textlintは、文章を『読む』ツールです」
- 「でも、人間の読み方とは違います」
- 「人間は意味を理解して読みます。textlintはAST、抽象構文木を解析して読みます」
- 「MarkdownをASTに変換し、そのASTに対してルールを適用します」
- 「これにより、構文を理解した品質検証ができます」
- 「正規表現ではなく、構文解析を使うことで、false positiveを避けられます」
- 時間: 1分

## Slide 21: 設計判断 - No core rules戦略

### ビジュアル
- 従来のLinterとtextlintの比較図
- プラグインアーキテクチャの図

### コンテンツ

```
No core rules戦略

❌ 従来のLinter：
インストール → すぐ使える → 画一的
├─ デフォルトルールが押し付けられる
└─ カスタマイズが困難

✅ textlint：
インストール → 何も起きない → ルール選択
                              ↓
                         適切に使える
├─ ユーザーが明示的に選択
└─ 用途に最適化

「楽に使える」より「適切に使える」
```

### スピーカーノート
- 「textlintの最も重要な設計判断は『No core rules』です」
- 「従来のLinterは、インストールするとすぐ使えます。でも、デフォルトルールが押し付けられます」
- 「textlintは違います。インストールしても、何も起きません」
- 「ユーザーは、自分が必要なルールを明示的に選択する必要があります」
- 「不便に見えますよね？でも、これが重要なんです」
- 「『楽に使える』より『適切に使える』ことを優先しました」
- 「この設計判断の理由は、次のスライドで説明します」
- 時間: 1分

## Slide 22: 排除した心理的プレッシャー

### ビジュアル
- プレッシャーを表すアイコン（×印）
- エコシステムの成長を表す図（○印）

### コンテンツ

```
心理的プレッシャーの排除

❌ 排除したもの：
「全てのルールに対応しなければならない」
という義務感

問題点：
• コアにIssueが押し寄せる
• 膨大なIssueを捌くのは無理
• メンテナンスが困難

✅ 実現したこと：
• コミュニティで100以上のルール作成
• エコシステムの成長
• 持続可能なメンテナンス
```

### スピーカーノート
- 「なぜNo core rulesなのか？」
- 「それは、『全てのルールに対応しなければならない』という心理的プレッシャーを排除するためです」
- 「もしコアルールを持っていたら、『このルールも追加してほしい』『このルールを修正してほしい』というIssueが押し寄せます」
- 「ESLintやBiomeを見てください。膨大なIssueを捌いています」
- 「私一人では、それは無理だと判断しました」
- 「No core rulesにすることで、このプレッシャーを排除しました」
- 「結果として、コミュニティで100以上のルールが作られ、エコシステムが成長しました」
- 「これが、持続可能なメンテナンスの鍵です」 <- [textlint - Linterの作り方](https://azu.github.io/slide/2022/lint-night/textlint.html)
