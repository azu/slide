## Slide 51: 続けることで複利が生まれる

### ビジュアル
- 複利効果の4つの軸を図示
- 15年間の成長曲線

### コンテンツ

```
続けることで複利が生まれる

15年間の継続が生んだ4つの複利効果：

1. データセット蓄積
   • JSer.info: 14年分のデータセット
   • textlint: 100以上のルール
   • jsprimer: Living Standardの実現

2. エコシステム成長
   • コミュニティ主導の品質基準
   • プラグインアーキテクチャの成功
   • 100人以上のコントリビューター

3. AI時代への適応力
   • JSer.info MCP、textlint MCP
   • jsprimer AI Agent統合
   • 継続のボトルネックをAIで解消

4. プロジェクト間の相互強化
   • 技術的依存の循環
   • 使っているから続く
   • 続いているから使う

継続 → 蓄積 → 複利 → 適応力
```

## Slide 52: そのための設計原則

### ビジュアル
- 技術的依存vs心理的依存の対比図（Part 4 Slide 46の再掲）
- 3つのプロジェクトの具体例

### コンテンツ

```
そのための設計原則

15年継続を可能にした設計思想：

技術的依存：積極的に育てる ✓
  ├ プロジェクト間の相互依存
  ├ エコシステムの成長
  ├ コミュニティとの協働
  └ → 複利効果を生む

心理的プレッシャー：意識的に排除する ✗
  ├ 「〜しなければならない」義務感
  ├ 一度破ると復帰が難しい固定スケジュール
  ├ 燃え尽きの原因
  └ → 継続を困難にする

具体的な実践：
• JSer.info: データドリブン公開
• textlint: No core rules戦略
• GitHub Sponsors: 見返りを用意しない

効率化ではなく持続可能性を設計する
```

### スピーカーノート
- 「そのための設計原則をお話しします」
- 「15年継続を可能にした設計思想は、2つあります」
- 「1つ目は、技術的依存を積極的に育てることです」
- 「プロジェクト間の相互依存、エコシステムの成長、コミュニティとの協働」
- 「これらは複利効果を生みます」
- 「2つ目は、心理的プレッシャーを意識的に排除することです」
- 「『〜しなければならない』という義務感」
- 「一度破ると復帰が難しい固定スケジュール」
- 「これらは燃え尽きの原因になり、継続を困難にします」
- 「具体的には、JSer.infoはデータドリブン公開、textlintはNo core rules戦略、GitHub Sponsorsは見返りを用意しない、という実践です」
- 「効率化ではなく、持続可能性を設計することが重要なんです」
- 時間: 1分15秒

## まとめセクションサマリー

**合計時間**: 3分  
**スライド数**: 3枚（Slide 51-53）  

**キーメッセージ**:
1. **複利効果の4つの軸**:
   - データセット蓄積
   - エコシステム成長
   - AI時代への適応力
   - プロジェクト間の相互強化

2. **設計原則の2つの軸**:
   - 技術的依存：積極的に育てる（複利効果）
   - 心理的プレッシャー：意識的に排除する（燃え尽き防止）

3. **聴衆への問いかけ**:
   - 自分のプロジェクトの「心理的依存」を見直してみては？
   - 何が「〜しなければ」になっているか？
   - それは設計で排除できないか？

**伝えたい核心**:
> 効率化ではなく持続可能性を設計する。継続が複利を生み、AI時代への適応力を生む。

**発表全体の流れ（復習）**:
```
イントロ（5分）
  ↓
Part 1: JSer.info - 読む技術（10分）
  読む70% / 書く20% / 伝える10%
  ↓
Part 2: textlint - 書く技術（10分）
  読む30% / 書く50% / 伝える20%
  ↓
Part 3: jsprimer - 伝える技術（12分）
  読む20% / 書く30% / 伝える50%
  ↓
Part 4: 循環の技術（10分）
  複利効果と設計原則
  ↓
まとめ（3分）
  持続可能性の設計思想
```

**次のアクション（聴衆に持ち帰ってほしいこと）**:
1. 自分のプロジェクトの心理的プレッシャーを特定する
2. 設計で排除できないか考える
3. 技術的依存を育てる機会を探す
4. Public Writingを始める・続ける

**補足資料・質疑応答の準備**:
- 各プロジェクトの詳細な技術スタック
- GitHub Sponsorsの具体的な収支
- AI統合の技術的詳細
- コミュニティ運営のノウハウ

**全発表の時間配分確認**:
- イントロ: 5分
- Part 1: 10分
- Part 2: 10分
- Part 3: 12分
- Part 4: 10分
- まとめ: 3分
- **合計: 50分** ← 40分の枠に対して10分オーバー

**⚠️ 時間調整の必要性**:
各Partで約2分ずつ削減する必要があります。特に：
- Part 1: 10分 → 8分（2分削減）
- Part 2: 10分 → 8分（2分削減）
- Part 3: 12分 → 10分（2分削減）
- Part 4: 10分 → 9分（1分削減）
- まとめ: 3分 → 3分（維持）
- 質疑応答: 2分（バッファ）

または、質疑応答を別枠とし、発表を40分ピッタリに収める調整が必要です。
