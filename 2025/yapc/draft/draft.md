## Why: なぜ持続可能性が重要なのか（5分 / 4スライド）

### スライド5: アウトプットではなくアウトカム
**アウトプット** = 作ったもの（記事、ツール、書籍）
**アウトカム** = 実際の影響・成果（信頼、エコシステム、教育効果）

**重要な洞察**：
> アウトカムが評価されるまでには時間がかかる

**例：エーザイの新薬開発**
- 開発には10年以上かかる
- 途中で止めると、アウトカムは生まれない
- 継続しないと、そもそもアウトカムにたどり着けない

### スライド6: OSSにおけるアウトカム
**時間をかけて現れるもの**：
- ツールの普及と影響
- コミュニティの形成
- 知識の蓄積と共有
- エコシステムの成長

**JSer.infoの例**：
- 1年目：個人の情報整理
- 5年目：JavaScript情報の参考元として認知
- 10年目：14年分のデータセット蓄積
- 14年目：AI時代のMCP統合で新しい価値

**これらはすべて、時間をかけないと現れない**

### スライド7: バーンアウトの問題
**多くのOSSプロジェクトの現実**：
- 数年で更新が止まる
- メンテナーの燃え尽き
- 心理的負担の増大

**なぜ燃え尽きるのか？**
→ 心理的プレッシャーの蓄積

**持続しないと**：
- アウトカムにたどり着けない
- 時間をかけた価値が生まれない

### スライド8: 持続可能性が必要な理由
```
継続 → 時間の経過 → アウトカムの顕在化
  ↑                      ↓
  ← 設計で支える ←  価値の認識
```

**核心の問い**：
どうやって15年間、燃え尽きずに継続できたのか？

→ 次のセクションで、その答えを明かします

## How: 持続可能性を実現する核心アイデア（6分 / 5スライド）

### スライド9: 核心の概念
**技術的依存を増やし、心理的依存を減らす**

これが15年間継続できた秘密

### スライド10: 技術的依存とは
**定義**：
- 自動化できる部分は自動化する
- ツールやシステムに頼る
- 再現可能なプロセス
- データの蓄積

**特徴**：
- スケールする
- 疲れない
- 複利効果を生む
- 他者も利用できる

**例**：
- RSSフィードの自動収集
- textlintによる文章校正
- CI/CDによる自動テスト

### スライド11: 心理的依存とは
**定義**：
- 「自分がやらなければ」というプレッシャー
- 完璧主義
- 義務感
- 外的報酬への依存

**特徴**：
- スケールしない
- 疲れる
- 燃え尽きにつながる
- 自分だけに依存

**例**：
- 「毎週月曜日に必ず公開」
- 「すべてのルールに対応しなければ」
- 「完璧な本を一度で書かなければ」

### スライド12: なぜこのバランスが重要か
```
技術的依存が高い
  ↓
長期的に継続できる
複利効果が生まれる

心理的依存が高い
  ↓
バーンアウトのリスク
途中で止まる
```

**これから3つのプロジェクトで具体例を見ていきます**

### スライド13: 今日の構成
```
1. JSer.info - 読む技術
   → データドリブン、効率性vs効果性
   
2. textlint - 書く技術
   → No core rules、エコシステム
   
3. jsprimer - 伝える技術
   → Living Standard、既知→未知
   
4. 相互作用と複利効果
   → 15年間の循環が生む価値
```

各プロジェクトで「技術的依存を増やし、心理的依存を減らす」具体例を見ます

## 読む技術: JSer.info（7分 / 9スライド）

### スライド14: JSer.info の本質
**2011年1月16日創刊**

**実績**：
- 750記事、14年継続
- 12,429サイト紹介
- 一度も欠かさず週刊配信
- 71万文字

**本質**：
> 整理されたデータである「情報」を伝えること

単にデータを並べるだけなら自動化で十分
エコシステムの理解には人間の判断が必要

**参考URL**: 
- https://jser.info/
- https://azu.github.io/slide/2016/jser5years/javascript-information.html

### スライド15: 情報収集システムの全体像
```
[3,600+ RSSフィード]
     ↓ 自動収集
[Inoreader：集約]
     ↓ ★人間の判断★
[Irodr：手動キュレーション]
     ↓
[Postem：執筆]
     ↓ 自動化
[GitHub Actions：公開]
```

**なぜ完全自動化しないのか？**
→ 効率性より効果性を優先

**参考URL**: 
- Irodr: https://github.com/azu/irodr
- Postem: https://github.com/azu/postem

### スライド16: 設計判断①データドリブンな公開基準
**心理的プレッシャーを排除**

```
❌ 従来：「毎週月曜日に公開」
   → 書けない週のプレッシャー
   → 一度破ると復帰困難

✅ JSer.info：「13記事集まったら公開」
   → 品質でリリース判断
   → 復旧可能性の向上
```

**コントロールできないものはコントロールしない**
- 毎週必ず13記事分の質の高い情報が見つかることは保証できない
- だから時間ではなくデータ量で判断

**結果**：14年間の継続

**参考URL**: https://jser.info/2017/01/15/jser-info-6years/

### スライド17: 効率性 vs 効果性
**効率性**：
- 物事を正しく行う
- 時間やリソースを削減
- 完全自動クロール

**効果性**：
- 正しいことをする
- ビジネス価値や顧客満足度
- 人間によるキュレーション

**JSer.infoの選択**：
効果性を優先

**なぜ？**
タッチポイントを増やすことで、情報の本質をより深く理解できる

### スライド18: 設計判断②退屈な部分だけ自動化
**技術的依存を増やす**

**自動化するもの**：
- 3,600フィードの収集（退屈）
- カテゴリ分類（退屈）
- GitHub Actions公開（退屈）

**手動で残すもの**：
- 価値判断（本質）
- ファクトチェック（本質）
- 文脈の理解（本質）

**トイル（定常作業）の削減**
→ 本質的なことに時間を使う

### スライド19: JSer.info Policy - 書く技術
> **「技術的な嘘はつかない」**

**実践内容**：
- パフォーマンス数値は必ず検証
- ベンチマークの事実確認
- 誇張表現を排除

**使わない言葉**：
"is Dead"、最強、熱い、これがベスト

**使う言葉**：
代替え方法、特徴、と比較して、現状

**結果**：
感情極性値 -0.216（ほぼ中立）

**参考URL**: https://jser.info/policy/

### スライド20: 「紹介」ではなく「知ってもらう」
**紹介**：
- 情報を提示して終わり
- 一方向の情報発信
- コンテンツの集約

**知ってもらう**：
- 読者が元サイトにアクセス
- JavaScriptエコシステム全体を理解
- 継続的な関わり

> 「真の目的はJavaScriptの情報を"紹介"ではなく"知ってもらう"事にあるため、継続的な活動が必要」

**JSer.infoは目的地ではなく、導線**

**参考URL**: https://jser.info/about/

### スライド21: 技術的依存を育てる - 複利効果
**14年間継続の結果**：

**JSer.info dataset**：
- 14年分のデータ蓄積
- 750記事、12,429サイト
- 構造化されたJSON

**AI時代への適応**：
- JSer.info MCP統合
- AIによるサマライズ
- 蓄積されたデータの再利用

**もし途中で辞めていたら、このデータセットは存在しなかった**

複利効果：過去の蓄積が未来の価値を生む

**参考URL**: https://github.com/jser/dataset

### スライド22: JSer.infoまとめ
**技術的依存を増やした**：
- データドリブンな公開基準
- 退屈な部分だけ自動化
- 小さなイテレーション
- データセットの蓄積

**心理的依存を減らした**：
- 「毎週月曜」プレッシャーの排除
- 完璧を求めない
- コミュニティに開く

**結果**：
14年継続 → 信頼の構築 → AI時代への適応

## 書く技術: textlint（7分 / 10スライド）

### スライド23: 読むから書くへの移行
**きっかけ**：

### スライド24: 書くことで気づいたこと
> **書くと、読む量が増える**

**なぜ？**
- 調べる（情報を読む）
- 検証する（ドキュメントを読む）
- 自分が書いたものを読み返す
- レビューで他人の文章を読む

**書くことは、読むことの延長**

### スライド25: 書く中で見つけた課題
**Promise本執筆時の問題**：
- 表記揺れが気になる
- 「JavaScript」vs「Javascript」
- 「コールバック」vs「callback」
- 読みやすさへのこだわり

**解決策**：ツールを作ろう

**参考URL**: https://azu.github.io/promises-book/

### スライド26: textlint誕生の5日間

### スライド27: textlintの本質
> 「自然言語には正解がないため、拡張の柔軟性を持つこと」

**コア原則**：
- 検証できることだけを自動化
- ルールの透明性
- 説明可能性

**AST（抽象構文木）ベースの処理**：
```
文章 → Markdown Parser → AST → ルール適用 → エラー検出
```

正規表現ではなく構文解析
→ 文脈を理解した検証

**参考URL**: https://textlint.github.io/

### スライド28: 設計判断①No core rules戦略
**心理的プレッシャーを排除**

```
❌ 従来のLinter：
   インストール → デフォルトルール → すぐ使える
   → 「全てのルールに対応しなければ」というプレッシャー

✅ textlint：
   インストール → 何も起きない → ルール選択
   → エコシステムに委ねる
```

**「楽に使える」より「適切に使える」**

すべてのユーザーが異なる要件
→ 意識的な選択を強制

### スライド29: 設計判断②最小コア、豊かなエコシステム
**技術的依存をコミュニティに拡散**

```
┌─────────────────────┐
│  100+ Community Rules │ ← ドメイン特化
├─────────────────────┤
│  4つの拡張ポイント    │
│ • Rules • Filters   │
│ • Presets • Processors │
├─────────────────────┤
│  @textlint/kernel   │ ← ミニマルコア
└─────────────────────┘
```

**コア設計思想**：
- 本体は最小限
- イノベーションはエコシステムで
- メンテナーの負担分散

**結果**：
週85,000ダウンロード、100以上のルール

## 伝える技術: jsprimer（8分 / 12スライド）

### スライド33: 書くから伝えるへの移行
**転換点**：
- 個人で書く → 相手に伝える
- 一人で書く → 共著で書く
- **「読者」を強く意識する瞬間**

**2016年**：JavaScript Primer開発開始

### スライド34: jsprimerの本質
**3つを継続的に提供**：
1. **書き方**：基本文法などのJavaScriptの書き方
2. **作り方**：JavaScriptを使ったアプリケーションの作り方
3. **学び方**：JavaScriptの進化を自分で知る学び方

**JavaScriptのアンカー（基準点）**：
- ECMAScriptは毎年更新される
- 初心者がどこを見ればいいかわからない
- 変化の中での基準点が必要

**参考URL**: https://jsprimer.net/

### スライド35: 設計判断①Living Standard戦略
**心理的プレッシャーを排除**

```
❌ 「完璧な本を一度で書く」プレッシャー

✅ Living Standard：継続更新を前提

従来の書籍：スナップショット（出版したら終わり）
  ↓
jsprimer：Living Standard
  ├─ Web版：常に最新（jsprimer.net）
  └─ 書籍版：年次スナップショット
```

**教科書もLiving Standardであるべき**

**実績**：
- v6.0.0：ES2024対応（2024年）
- v7.0.0：ES2025対応（2025年8月）
- 10年間の継続的追跡

### スライド36: 設計判断②Design Doc
**心理的プレッシャーを軽減**

```
❌ 「どう書くか」で迷うプレッシャー

✅ Design Doc：方向性を明確化してから執筆

各章/
├── README.md（本文）
├── OUTLINE.md（設計文書）
└── 議論の履歴（Issue/PR）
```

**OUTLINE.mdの役割**：
- なぜこの章が必要か
- 何を学ぶか
- どう教えるか
- 100人以上との共通理解

**参考URL**: https://github.com/asciidwango/js-primer/tree/master/source

### スライド37: AI活用 - Iterator Helpers章
**2025年8月の進化**：
```
Design Doc（人間）
  ↓
AI Agentで初稿生成
  ↓
レビュー・修正（人間）
```

**文章の「最初の一歩」は重い**
→ このボトルネックをAIで軽減

**結果**：
- AIは冗長な文章を書く傾向
- レビューと修正で行数を削減
- 2025年時点での持続可能性の進化

**参考URL**: https://efcl.info/2025/08/18/jsprimer-v7/

### スライド38: 設計判断③既知→未知の原則
**書きやすさより読みやすさ**

```
❌ 「これを覚えろ」（著者視点）

✅ 「あなたが知っているXは、実はY」（読者視点）
```

**読者の現在地から出発**

**実践**：
- 何十回も読み返す
- 読者として読む
- 読まないと書けない

### スライド39: 自動テストによる品質保証
**3層の品質チェック**：
```
1. textlint：文章品質
   ↓
2. power-doctest：コード検証
   ↓
3. textstat：複雑度管理
```

すべてCI/CDで自動実行

**技術的依存の活用**：
- textlint（自分が作ったツール）
- power-doctest（自分が作ったツール）
- HonKit（自分がメンテしているツール）

使っているから続く、続いているから使う

### スライド40: Sandpack統合（2022年）
**ブラウザ内ライブ実行**：
- コード例をその場で実行
- Contribute障壁の最小化
- GitHubだけで編集完結

**技術的ハードルの低下**
→ より多くの貢献者

**参考URL**: https://jsprimer.net/
