# JSer.info Policy

**「技術的な嘘はつかない」**

^ JSer.infoには、明文化された行動指針があります。それが「JSer.info Policy」です。最も重要な原則は「技術的な嘘はつかない」です。

- パフォーマンス数値は必ず検証
- ベンチマークの事実確認
- 誇張表現を排除

^ パフォーマンス数値は必ず自分で検証します。「このライブラリは10倍速い」という主張があれば、実際にベンチマークを確認します。誇張表現も排除します。

**結果**:
感情極性値 -0.216（ほぼ中立）

^ 感情極性値を分析したところ、-0.216とほぼ中立的でした。この一貫性が、14年間の信頼を築いてきました。

# 「紹介」ではなく
# 「知ってもらう」

[.column]

**紹介**
情報を提示して終わり

↓

**知ってもらう**
読者が元サイトにアクセスし、
エコシステムを理解する

^ JSer.infoの目的は、単に情報を「紹介」することではありません。「知ってもらう」ことです。紹介は、情報を提示して終わりです。一方向の情報発信です。知ってもらうは、読者が元のサイトにアクセスし、JavaScriptエコシステム全体を理解することを意味します。JSer.infoは目的地ではなく、導線なんです。だからこそ、継続的な活動が必要になります。

# データドリブン公開

**❌ 従来**
毎週月曜日に公開
→ 書けない週のプレッシャー

^ JSer.infoの最も重要な設計判断の一つが、「データドリブンな公開基準」です。従来のやり方なら「毎週月曜日に公開」とスケジュールを決めますよね。でも、これには問題があります。書けない週があると、大きなプレッシャーになります。そして一度破ると、復帰するのが難しくなります。

**✅ JSer.info**
13記事集まったら公開
→ 品質でリリース判断

^ JSer.infoは違います。「13記事集まったら公開」というデータ量で判断します。これにより、品質を優先しつつ、もし休んでも復帰しやすい設計になっています。コントロールできないもの、例えば「毎週必ず13記事分の質の高い情報が見つかる」ということは、コントロールしようとしないのです。

**排除したもの**
「毎週月曜に公開しなければならない」

^ この設計判断の本質は、「心理的プレッシャーの排除」です。「毎週月曜に公開しなければならない」という義務感は、強力なプレッシャーです。このプレッシャーが燃え尽きを招きます。

**実現したこと**
- 復旧可能性の向上
- 14年間の継続
- 心理的な持続可能性

^ データドリブンな基準にすることで、このプレッシャーを排除しました。結果として、14年間継続できています。これが、持続可能性を設計するということです。

# 効率性 vs 効果性

[.column]

**効率性**
物事を正しく行う
→ 完全自動クロール

**効果性**
正しいことをする
→ 人間によるキュレーション

^ ここで重要な区別をします。効率性と効果性の違いです。効率性は「物事を正しく行う」こと。時間やリソースを削減することです。効果性は「正しいことをする」こと。ビジネス価値や顧客満足度を高めることです。JSer.infoで言えば、完全自動クロールは効率的です。でも、人間がキュレーションする方が効果的なんです。

**JSer.infoの選択**
効果性を優先

^ なぜなら、タッチポイントを増やすことで、情報の本質をより深く理解できるからです。効率化ではなく、効果性を追求することが、持続可能性につながります。

# textlintの本質

「自然言語には正解がないため、
 拡張の柔軟性を持つこと」

**従来**

# 心理的プレッシャーの排除

**排除したもの**
「全てのルールに対応しなければ」

^ なぜNo core rulesなのか？それは、「全てのルールに対応しなければならない」という心理的プレッシャーを排除するためです。もしコアルールを持っていたら、「このルールも追加してほしい」「このルールを修正してほしい」というIssueが押し寄せます。ESLintやBiomeを見てください。膨大なIssueを捌いています。私一人では、それは無理だと判断しました。

**実現したこと**
- コミュニティで100以上のルール作成
- エコシステムの成長
- 持続可能なメンテナンス

^ No core rulesにすることで、このプレッシャーを排除しました。結果として、コミュニティで100以上のルールが作られ、エコシステムが成長しました。これが、持続可能なメンテナンスの鍵です。
